# PRD — Intent-Driven Travel Discovery
**Version:** 0.1  
**Status:** Draft  
**Authors:** Hackathon team  

---

## 1. Problem statement

Skyscanner's current search experience requires users to know what they want before they search — origin, destination, dates. This works for high-intent searches but fails the large portion of travellers who have a feeling or vibe but not a specific destination in mind.

Savvy Search partially addresses this with natural language input, but its output is three destination cards generated by a general-purpose LLM with no grounding in live pricing, no session persistence, and no ability to refine. The user gets suggestions, not a conversation.

The result is a gap: travellers with exploratory intent are poorly served, and those who do use Savvy Search have no path from "interesting suggestion" to "confident booking decision" within the same experience.

---

## 2. Goal

Build a session-based, intent-driven discovery experience that:
- Accepts natural language input describing a travel vibe
- Returns destination and hotel recommendations grounded in live Skyscanner flight and hotel data
- Shows the user what the system understood and lets them correct it
- Allows progressive refinement without losing session context
- Ends with a clear path to booking on Skyscanner

---

## 3. Users

**Primary:** Exploratory travellers — people who know roughly what kind of trip they want but not a specific destination. Holiday planners browsing options 4–12 weeks out.

**Secondary:** Directional travellers — people who have a destination in mind and want to validate it against budget and find accommodation.

---

## 4. Use cases

### UC1 — Vague exploratory with mid-session refinement

**Entry point:** Search bar on Skyscanner homepage or trips tab  
**Input:** "niche countryside in the alps"  

**Happy path:**
1. Intent extracted: places = [Ötztal Valley, Dolomites, Triglav foothills, Aosta Valley], vibe = [rural, off-beaten-path, nature, quiet], specificity = exploratory
2. Intent tags shown in panel — user sees what the system understood
3. Flight prices retrieved for nearest hubs per place
4. Hotels scored against vibe using pre-stored embeddings + keyword matching
5. Ranked result cards shown — each with place name, indicative flight price, indicative hotel range, one-line explanation
6. User types: "narrow it down to north of Italy"
7. Intent struct diffed — countries updated to [Italy], places narrowed to [Dolomites, Aosta Valley]
8. Results update — session badge remains active
9. User taps "cheapest month" on Dolomites card
10. Month-by-month price chart shown inline

**Success:** User identifies a destination they feel confident about and understands why it was recommended.

---

### UC2 — Directional with budget constraint

**Entry point:** Same search bar  
**Input:** "weekend in Slovenia, budget €300 total"  

**Happy path:**
1. Intent extracted: places = [Ljubljana, Lake Bled, Soča Valley], countries = [Slovenia], budget = 300, specificity = specific
2. Specificity classifier routes to package view
3. Flights Indicative + Hotels Indicative called — combined cost checked against €300
4. Package card shown: flight to Ljubljana + hotel range, total within budget, explanation
5. User types: "direct flights only"
6. Intent diffed — direct_only flag added
7. Results update with nonstop filter applied
8. User clicks "Search on Skyscanner" → shallow link opens Skyscanner live search pre-filled

**Success:** User lands on Skyscanner live search with correct parameters pre-populated.

---

### UC3 — Open destination, flexible dates

**Entry point:** Same search bar  
**Input:** "somewhere warm, I'm flexible on when"  

**Happy path:**
1. Intent extracted: vibe = [warm, relaxed], dates = null, specificity = exploratory
2. Anywhere query returns global candidates filtered by climate proxy
3. Indicative by month called for top candidates — cheapest month found per destination
4. Cards shown with "best time to go" signal: "Marrakech — April, from €89"
5. User types: "which of these is least touristy in that month"
6. Intent diffed — crowd_pref = low added
7. Hotel keyword scores re-applied with crowd signal weighted higher
8. Results re-ranked, order may change

**Success:** User finds a destination + optimal travel window they would not have discovered through traditional search.

## 5. Feature requirements

### 5.1 Intent extraction
- System must accept free-text input of any length
- System must extract: places, countries, start_date, end_date, budget, vibe, specificity
- Places must reflect the vibe — a skiing query should return ski resorts, not cities
- Specificity must be classified as one of: exploratory, directional, specific
- Extraction must complete in under 3 seconds

### 5.2 Session and refinement
- Each search creates a session with a unique ID
- Session persists the intent struct and result set across refinement turns
- Refinement input must produce a diff against the existing struct, not a full reset
- Intent tags must be shown to the user as removable chips
- Removing a tag must trigger a result refresh

### 5.3 Candidate generation
- System must resolve each place to a nearest Skyscanner hub entity ID via Autosuggest
- System must retrieve indicative flight prices for each resolved hub
- Places with no flight data must remain in the result set with a null price, ranked lower
- Date aggregation (by month) must be available for any result card on demand

### 5.4 Hotel matching
- Each candidate place must have at least one hotel scored against the intent vibe
- Scoring must combine pre-stored embedding similarity and keyword-sentiment matching
- Keyword matching must operate on sentiment-bucketed text — negated keywords must not positively score
- Pre-stored embeddings must cover the destination corpus used in the demo
- Hotel scoring must not add latency to the main query path — all vectors pre-stored

### 5.5 Ranking
- Final score must incorporate: hotel match score, price fit, flight availability
- Places exceeding budget must not be excluded — they must appear ranked lower with a visual indicator
- Specificity = specific must trigger combined flight + hotel cost check against budget

### 5.6 Explanation
- Every result card must show a one-line explanation referencing the user's own vibe tags
- Explanation must not be generic destination copy
- Explanation must be generated by the LLM using the intent struct as context

### 5.7 Handoff
- Every result card must have a shallow link CTA
- Shallow link must pre-fill origin, destination, and dates where available
- For UC2 (specific), shallow link must open live search, not indicative

---

## 6. Non-requirements

The following are explicitly out of scope for this build:

- User authentication or persistent cross-session history
- Car hire or multi-city routing
- Hotels Live Prices (indicative is sufficient)
- Group trip coordination
- Native mobile implementation
- Carrier name resolution (entity codes acceptable in demo)

---

## 7. Success metrics

For the hackathon demo, success is qualitative:

- All three use case happy paths complete end-to-end without manual intervention
- Intent tags correctly reflect what was typed in all three inputs
- Refinement turns update results visibly and correctly
- At least one result per use case has an explanation that references a specific vibe tag from the input
- UC2 shallow link opens a valid Skyscanner search page
